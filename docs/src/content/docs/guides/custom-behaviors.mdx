The built-in behaviors cover gravity, drag, fading and scaling. For anything else, like wind, wobbling or color-related transformations, you can write your own. This guide builds a bubble effect step by step: bubbles that rise from a button and sway from side to side on their way up. It assumes you know how [behaviors work](/concepts/behaviors/), and how to set up an effect with [`createEffect()`](/api/custom_effects/createeffect/).

## Start with an effect

Behaviors are only available to custom effects, so the first step is to build an effect to add them to. These bubbles start at the button, rise thanks to a negative gravity, and fade out at the end:

<LiveDemo demo="bubbles-basic" size="compact" label="Basic bubbles" icon={BubblesIcon} />

The bubbles rise, but in perfectly straight lines. To add some life to them, we would like to have them sway from left to right on their trip upwards, and no built-in behavior does that.

## A behavior is a function

The simplest behavior is a function. party.js calls it for every particle, on every simulation step, with the particle and a [context](/api/behaviors/behaviorupdatecontext/). Here's one that pushes particles to the right, like a steady breeze:

```js
const breeze = (particle, ctx) => {
	particle.velocity = {
		...particle.velocity,
		x: particle.velocity.x + 100 * ctx.dt,
	};
};
```

`ctx.dt` is the length of the step, in seconds. Anything that's meant to happen *per second* should be multiplied by it to keep effects framerate-independent. Here, the breeze adds 100 pixels per second to the speed, every second. Without `dt`, it would add 100 on every step, 120 times a second.

The new velocity is a new object, built from the old one. That's the way the built-in behaviors change values, and it keeps your behavior from accidentally changing a value that's shared with something else.

:::tip
When using TypeScript, give the function the [`Behavior`](/api/behaviors/behavior/) type, and the particle and context are typed for you.
:::

## Taking options

To make the strength adjustable, wrap the behavior in a function that takes the options, and returns the behavior. All built-in behaviors are written this way.

## Storing data per particle

A breeze pushes every bubble the same way. To make them sway from side to side instead, each bubble can follow a wave over time, `Math.cos(particle.age * 3)`. But then all bubbles would sway in sync, which would look too stiff. To solve this, we assign each bubble a random **phase** when it spawns, which it can store and access later on.

For that, a behavior can be an object instead of a function. Its `init` function runs once for each particle, right after it spawns, and its `update` function runs on every step, like a plain behavior function would. Each particle has a [`data`](/api/particles/particle/#data) map, where behaviors can store values of their own:

<LiveDemo demo="bubbles-sway" size="compact" label="Blow bubbles" icon={BubblesIcon} />

Two notes on the implementation:

- **The key is a `Symbol`**, created inside the outer function. Every call of `sway()` creates a new one, so two sways in the same effect, or another behavior that stores data, never overwrite each other's values. A string key like `"phase"` could clash.
- **The phase comes from `ctx.rng`**, the effect's random number generator, and not from `Math.random()`, to keep the effect [reproducible](/concepts/samplers/#reproducible-randomness).
- **Per-particle values live on the particle**, not in variables of the outer function. `sway(200)` is called once, and the behavior it returns then runs for every particle of the effect, so a variable would be shared by all of them.

## More examples

A behavior can change any of the particle's properties. Here are a few more ideas to build on.

### Ending particles early

A behavior can end a particle before its lifetime is up, by setting its `age` to its `lifetime`. It's then removed at the end of the step. For example, to remove particles once they've fallen 200 pixels below the origin:

<LiveDemo demo="behavior-floor" size="compact" label="Floored" icon={MinusIcon} />

Positions are in particle space, measured from the origin, with +y pointing up, so the floor is at a negative y.

### Changing color over time

Colors are stored as [`Color`](/api/utilities/color/) objects, in the OKLab color space. To shift each particle towards another color over its lifetime, remember the color it started with, and blend from there:

<LiveDemo demo="behavior-shift-color" size="compact" label="Color shift" icon={PaletteIcon} />

It keeps the particle's current opacity, and `fade()` only changes the opacity, so the two can be combined in either order.

### Steering towards a point

A behavior can also push particles towards a point, here with a constant acceleration of `strength` px/s².

Like the floor, the `point` is in particle space, relative to the origin.

## Things to keep in mind

- **Keep updates cheap.** An update runs for every particle, 120 times a second. Don't read from the page in it, for example with `getBoundingClientRect()`. Ideally you would measure once, in the outer function, and use the result.
- **Errors stop the effect.** If a behavior throws, the effect is stopped right away, and its [`finished`](/api/effects/effect/) promise resolves with `"stopped"`. The error is reported in the console, and other effects keep running.
- **Behaviors don't run on dead particles.** Once a particle's `age` reaches its `lifetime`, it's removed at the end of the step, without a final update. A behavior that needs to do something at the very end has to do it during the last moments of the lifetime, like `fade()` does.
